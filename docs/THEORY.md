# Теория к защите: умные указатели

Шпаргалка по вопросам, которые вероятны на сдаче. Ссылки на код - в квадратных скобках.

## 1. Зачем нужны умные указатели

Сырой указатель `T*` не знает, кто владеет объектом и когда его удалять. Отсюда типичные
ошибки: **утечка** (забыли `delete`), **двойное удаление**, **висячий указатель**
(обращение к уже удалённому объекту), `delete` вместо `delete[]`, утечка при исключении
между `new` и `delete`.

Умный указатель - класс, который владеет объектом и удаляет его **в деструкторе**.
Это идиома **RAII** (Resource Acquisition Is Initialization): ресурс захватывается в
конструкторе и освобождается в деструкторе, а деструктор локального объекта вызывается
всегда - при выходе из блока, при `return`, при исключении.

## 2. lvalue, rvalue и `&&`

- **lvalue** - выражение, у которого есть имя/адрес и которое живёт дальше текущего
  выражения: переменная `x`, `*p`, `a[i]`. Можно взять адрес `&x`.
- **rvalue** - временное значение, которое сейчас исчезнет: `42`, `x + 1`, `MakeUnq<int>(5)`,
  результат функции, возвращающей по значению.
- `T&` - **lvalue-ссылка**, привязывается только к lvalue (кроме `const T&`, которая
  привязывается и к rvalue).
- `T&&` - **rvalue-ссылка**, привязывается только к rvalue. Смысл: «этот объект временный,
  у него можно забрать ресурсы».

**Важно:** у самой переменной типа `T&&` есть имя, поэтому внутри функции она - lvalue.
Чтобы передать её дальше как rvalue, нужен `std::move`.

**`std::move(x)`** ничего не перемещает - это просто приведение `static_cast<T&&>(x)`.
Оно разрешает выбрать перегрузку с `T&&` (конструктор/присваивание перемещением).
После перемещения объект-источник остаётся в корректном, но «пустом» состоянии - у нас
`UnqPtr`/`ShrdPtr` после `std::move` становятся `nullptr` (это проверяют тесты
`MoveConstructorTransfersOwnership`, `MoveDoesNotChangeCount`).

**`std::forward<Args>(args)...`** [MakeUnq, MakeShrd] - «идеальная передача»: в шаблоне
`Args&&` (forwarding reference) сохраняет категорию аргумента: lvalue передаётся как lvalue,
rvalue - как rvalue. Так `MakeUnq<T>(args...)` вызывает ровно тот конструктор `T`,
который вызвал бы прямой `new T(args...)`.

## 3. Семантика перемещения в нашем коде

**UnqPtr** - объектом владеет ровно один указатель, поэтому:
```cpp
UnqPtr(const UnqPtr&) = delete;              // копировать нельзя: было бы два владельца
UnqPtr(UnqPtr&& other) noexcept              // перемещать можно: владелец меняется
    : pointer_(other.Release()) {}
```
`UnqPtr<int> b = a;` - ошибка компиляции; `UnqPtr<int> b = std::move(a);` - работает,
`a` становится пустым.

**ShrdPtr** - перемещение не меняет счётчик (владельцев столько же, просто другой объект
`ShrdPtr` держит ссылку), а копирование увеличивает его на 1. Поэтому перемещение дешевле:
нет записи в счётчик.

**Почему `noexcept`**: `std::vector` при росте перемещает элементы, только если
конструктор перемещения `noexcept`, иначе копирует (чтобы сохранить строгую гарантию
исключений). Для `ShrdPtr` копирование - это лишние `++`/`--` счётчика.

## 4. Правило пяти

Если класс управляет ресурсом, ему нужны: деструктор, конструктор копирования,
присваивание копированием, конструктор перемещения, присваивание перемещением.
- `UnqPtr`: деструктор + перемещение; копирование явно `= delete`.
- `ShrdPtr`: все пять.
- `DynamicArray`: деструктор `= default` (память освобождает поле `UnqPtr<T[]>`),
  копирование глубокое, перемещение, присваивание через copy-and-swap.

## 5. Подсчёт ссылок (ShrdPtr)

Поля: `T* pointer_` и `std::size_t* referenceCount_` (вариант 3 ТЗ). Счётчик - в куче,
общий для всех копий.

| Операция | Счётчик |
|---|---|
| `ShrdPtr(new T)` | выделяется, = 1 |
| копирование | `++` |
| перемещение | не меняется (источник обнуляется) |
| деструктор, `Reset`, `= nullptr` | `--`; при 0 - `delete pointer_` и `delete referenceCount_` |
| пустой указатель | счётчик не выделяется (`nullptr`), `UseCount() == 0` |

Все операции со счётчиком - **O(1)**.

**Ограничение - циклические ссылки.** Если объект A хранит `ShrdPtr` на B, а B на A,
счётчики никогда не станут 0 - утечка. В STL для этого есть `weak_ptr` (ссылка без
владения); по условию задания `weak_ptr` не реализуем.

## 6. Присваивание самому себе

Из заметок: `p = p` при счётчике 1. Наивная реализация «сначала отпустить старый, потом
захватить новый» удалит объект (счётчик 1 → 0), а затем попытается сослаться на него.

```cpp
ShrdPtr& operator=(const ShrdPtr& other) noexcept
{
    if (this != &other)        // p = p - ничего не делаем
    {
        ShrdPtr copy(other);   // 1) захватываем новый объект (счётчик++)
        Swap(copy);            // 2) обмениваемся содержимым с копией
    }                          // 3) деструктор copy отпускает СТАРЫЙ объект
    return *this;
}
```
Это идиома **copy-and-swap**: сначала создаётся копия (если бросит исключение - `*this`
не изменился), потом обмен, потом старое значение уничтожается вместе с временной копией.
Она корректна даже без `if` и даже когда `this` и `other` - разные `ShrdPtr` на один объект;
проверка `if` экономит лишние `++`/`--`.
Тесты: `SelfCopyAssignmentKeepsObject`, `AssignmentBetweenOwnersOfSameObject`, `SelfMoveAssignmentKeepsObject`.

`UnqPtr::Reset(p.Get())` тоже защищён: если новый указатель совпадает с текущим, ничего не
удаляется (иначе - двойное удаление).

*Голуб, правило 124* советует возвращать из `operator=` ссылку на константу. Мы возвращаем
`ShrdPtr&` (неконстантную): так делает стандартная библиотека, и этого требуют
стандартные контейнеры и алгоритмы.

## 7. Подтипизация

Требование ТЗ: если `Derived` - подкласс `Base`, то `ShrdPtr<Base> p = ShrdPtr<Derived>(...)`
работает, а для несвязанных типов - нет.

`ShrdPtr<Base>` и `ShrdPtr<Derived>` - **разные, никак не связанные классы** (шаблон не
наследует подтипизацию аргументов). Поэтому нужен шаблонный конструктор:
```cpp
template <typename U, typename = std::enable_if_t<std::is_convertible<U*, T*>::value>>
ShrdPtr(const ShrdPtr<U>& other) noexcept;
```
- `std::is_convertible<U*, T*>` - истинно, если `U*` неявно приводится к `T*`, т.е. `U`
  наследник `T` (или тот же тип).
- `std::enable_if_t<false>` не существует → подстановка шаблона не удаётся → конструктор
  **исключается из перегрузки** (SFINAE - Substitution Failure Is Not An Error) →
  `ShrdPtr<Tracked> p = ShrdPtr<Unrelated>()` - ошибка компиляции.
- Конструктор обращается к закрытым полям `ShrdPtr<U>` - для этого объявлено
  `template <typename U> friend class ShrdPtr;`.

Проверка - `static_assert` в начале тестов (`is_constructible`, `is_assignable`): код,
который **не должен** компилироваться, проверяется на этапе компиляции.

**Для массивов подтипизации нет.** `Derived[]` нельзя трактовать как `Base[]`: если
`sizeof(Derived) > sizeof(Base)`, то `array[1]` через `Base*` попадёт в середину первого
элемента, а `delete[]` вызовет не те деструкторы. Конструктор `template <typename U>
explicit UnqPtr(U*) = delete;` запрещает `UnqPtr<Base[]>(new Derived[n])`.

**Виртуальный деструктор.** `UnqPtr<Base>`, созданный из `Derived`, удаляет объект через
`delete (Base*)`. Это корректно, только если у `Base` виртуальный деструктор (у `Tracked`
он есть). `std::shared_ptr` запоминает «правильный» deleter и обходится без этого - у нас
deleter'ов нет, это упрощение.

## 8. Почему конструктор из `T*` - `explicit`

```cpp
void Use(ShrdPtr<int> p);
int* raw = new int(5);
Use(raw);   // без explicit скомпилировалось бы: создался бы временный ShrdPtr,
            // после вызова он удалил бы *raw - а raw всё ещё используется снаружи
```
`explicit` запрещает неявное превращение сырого указателя во владеющий.
Ещё одна ошибка, от которой защитить нельзя: два `ShrdPtr` из одного сырого указателя
(`ShrdPtr<int> a(raw), b(raw);`) - два счётчика, двойное удаление. Поэтому лучше
создавать через `MakeShrd`, а сырой указатель не хранить.

## 9. Безопасность при исключениях

- `ShrdPtr(T* p)`: если `new size_t` бросит `std::bad_alloc`, объект `*p` удаляется и
  исключение пробрасывается - утечки нет (иначе объект никому бы не принадлежал).
- `ShrdPtr(UnqPtr&&)`: счётчик выделяется **до** `unique.Release()` - если выделение не
  удалось, объектом по-прежнему владеет `UnqPtr`.
- `DynamicArray::Reallocate`: новый буфер выделяется до изменения состояния.
- `DynamicArray::Append(array[0])`: значение копируется до перевыделения, иначе ссылка
  указывала бы в удалённый буфер.

## 10. Сравнение с STL

| | наш `ShrdPtr` | `std::shared_ptr` |
|---|---|---|
| размер указателя | 16 Б (`T*` + `size_t*`) | 16 Б (`T*` + указатель на блок управления) |
| блок управления | `size_t` - 8 Б | 24 Б: vtable (deleter) + strong и weak счётчики + указатель (по замеру: 44 = 16 + 4 + 24) |
| счётчик | обычный | **атомарный** (потокобезопасный) |
| `weak_ptr`, deleter, aliasing | нет | есть |
| выделений при создании | 2 (объект + счётчик) | 2 через `new`, **1** через `make_shared` |

Отсюда результаты замеров:
- копирование/передача по значению: наш в **~4 раза быстрее** - атомарная операция
  (`lock add` / `lock xadd` на x86) дороже обычного инкремента;
- создание: одинаково с `shared_ptr(new T)`, но `make_shared` быстрее в ~2 раза -
  одно выделение памяти вместо двух; основное время - `malloc`/`free` (~50 нс);
- память: 28 Б на объект против 40-44 Б у STL;
- `UnqPtr` = сырой указатель по времени и памяти (вся логика встраивается компилятором).

**Плата за скорость:** `ShrdPtr` нельзя копировать одновременно из нескольких потоков -
счётчик испортится (гонка данных).

## 11. Как устроены замеры (если спросят)

- Медиана из 3-5 прогонов - устойчива к выбросам (другие процессы, планировщик ОС).
- При малых N прогон повторяется до ≥ 300 000 операций - иначе время меньше точности таймера.
- `DoNotOptimize` (пустая ассемблерная вставка) - иначе оптимизатор вправе выбросить пару
  `new`/`delete` или `++`/`--` и замер покажет 0.
- Сборка Release (`-O3`): в Debug нет встраивания, и сравнение нечестное.
- Память: глобальный `operator new` заменён и считает число вызовов и байты.

## 12. Проверка утечек

- **Тесты**: класс `Tracked` считает созданные и удалённые объекты; после каждого теста
  проверяется `created == destroyed` [tests/Tracked.h].
- **valgrind memcheck** - запускает программу на виртуальном процессоре и следит за каждым
  байтом кучи: утечки, двойное освобождение, чтение удалённой/неинициализированной памяти.
  Замедление ~20-50×, перекомпиляция не нужна.
- **AddressSanitizer** (`-fsanitize=address`) - компилятор вставляет проверки вокруг каждого
  обращения к памяти (теневая память): выход за границы, use-after-free, double free,
  `new`/`delete[]` mismatch; LeakSanitizer ищет утечки при выходе. Замедление ~2×.
- **UndefinedBehaviorSanitizer** (`-fsanitize=undefined`) - переполнение знаковых,
  сдвиги, неверные приведения, разыменование `nullptr` и т.п.
- **Контроль** - `LeakDemo` с намеренной утечкой: оба инструмента её находят, значит
  отчёт «0 ошибок» на наших тестах что-то значит.

## 13. Сложность операций

| Операция | Сложность |
|---|---|
| создание, копирование, перемещение, уничтожение `UnqPtr`/`ShrdPtr` | O(1) (+ стоимость `new`/`delete`) |
| `*`, `->`, `[]`, `Get`, `UseCount` | O(1) |
| `DynamicArray::Get/Set/[]` | O(1) |
| `DynamicArray::Append` | амортизированно O(1) (ёмкость удваивается) |
| `DynamicArray::Resize`, копирование | O(n) |

## 14. Вероятные вопросы

- **Чем `UnqPtr` отличается от `ShrdPtr`?** Один владелец и только перемещение против
  нескольких владельцев со счётчиком. `UnqPtr` ничего не стоит, `ShrdPtr` - +1 выделение и счётчик.
- **Когда объект удаляется?** `UnqPtr` - при уничтожении/`Reset`/присваивании владельца;
  `ShrdPtr` - когда счётчик становится 0, т.е. уничтожен последний владелец.
- **Что будет, если скопировать `UnqPtr`?** Ошибка компиляции: конструктор копирования `= delete`.
- **Зачем отдельные `UnqPtr<T>` и `UnqPtr<T[]>`?** Разное удаление (`delete` / `delete[]`),
  разные операции (`*`, `->` / `[]`), разная подтипизация. Сделано частичной специализацией шаблона.
- **Почему шаблоны в `.h`, а не в `.cpp`?** Код шаблона генерируется при подстановке
  конкретного типа в той единице трансляции, где он используется - компилятор должен видеть
  полное определение.
- **Почему `std::move` не перемещает?** Это только приведение к `T&&`; перемещает
  конструктор/оператор, выбранный по этой перегрузке.
- **Почему наш быстрее STL?** Неатомарный счётчик и отсутствие weak-счётчика/deleter'а.
  Цена - нет потокобезопасности и `weak_ptr`.
- **Почему `make_shared` быстрее при создании?** Одно выделение памяти вместо двух.
